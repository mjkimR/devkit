# [ARCH-08-2-resource-taxonomy] Agent Asset and Guidance Resource Taxonomy

**Scope**: Taxonomy, naming standards, and placement decision rules for agent guidance, operational playbooks, governance rules, and runtime assets.
**Related Documents**: `ARCH-05-4-distribution-components`

## 1. Design Objectives

The taxonomy prevents three antipatterns:

- **Context bloat**: voluminous policies in root instruction files (`AGENTS.md`, `CLAUDE.md`) consume context on every turn.
- **Fidelity confusion**: procedural checklists enforced through static linters, or machine-verifiable invariants left to prompt instructions.
- **Naming ambiguity**: single-word identifiers (`entrypoint`, `guide`, `agents`) blur agent personas, Python entry points and files.

It does so with a three-tier classification and self-describing kind names for every distributable agent resource managed by `devkit`.

## 2. The Three-Tier Resource Hierarchy

Lifecycle hooks are mechanized execution resources (`kind = "hook"`): a declarative host/event/handler definition
registers an installed service at a native host event. They are distinct from Git commit gates and do not grant
integration authority. Schema and placement: `CAP-HOST-lifecycle-observation`.

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│                       1. Guidance & Context Layer                            │
│  - host-guidance-block  : Host orientation marker (in root AGENTS.md)        │
│  - package-constitution : Package-level constitution (.devkit/.../AGENTS.md) │
│  - package-instruction  : Instruction headers; bodies loaded on demand       │
│  - package-playbook     : Occasional procedures (explicit or rule-triggered) │
│  - package-workflow     : Delivery workflow definition (devkit workflow)     │
│  - package-document     : Reference file read by path, or seeded once        │
└──────────────────────────────────────┬───────────────────────────────────────┘
                                       │
┌──────────────────────────────────────┴───────────────────────────────────────┐
│                       2. Mechanized Execution Layer                          │
│  - governance-rule      : Deterministic invariant (evaluated by devkit rules)│
│  - agent-skill          : Executable tool directory (.agents/skills/, etc.)  │
│  - agent-subagent       : Native agent persona config (.codex/agents/, etc.) │
│  - git-commit-gate      : Git hook policy (run by devkit gate)               │
│  - host-hook            : Native lifecycle event to installed service       │
└──────────────────────────────────────┬───────────────────────────────────────┘
                                       │
┌──────────────────────────────────────┴───────────────────────────────────────┐
│                       3. Packaging & Selection Layer                         │
│  - Asset Selectors: Manifest Presets & Project Configuration                 │
└──────────────────────────────────────────────────────────────────────────────┘
```

Each label maps to one manifest `kind` (see the `CAP-DIST-manifest-spec`): `instruction`, `playbook`, `workflow`, `document`, `rule`, `skill`, `subagent`, `gate` and `hook`. The host guidance block is generated by `devkit sync`; bundles contribute lines to it through `guidance` assets. A constitution is a bundle's `AGENTS.md`, not a declared asset.

## 3. Detailed Resource Kinds and Specifications

### A. Guidance & Context Layer (Natural Language)

#### 1. `host-guidance-block`
- **Role**: A concise marker block that `devkit sync` writes into the consumer repository's root `AGENTS.md` between managed delimiters:
  ```markdown
  <!-- DEVKIT:START -->
  ## devkit
  ... the once-per-bundle `devkit get-context` rule, the installed bundle names,
  ... the generated entry skills, the selected bundles' guidance fragments,
  ... and the "edit outside the markers" notice
  <!-- DEVKIT:END -->
  ```
- **Consumption**: Read by any agent session upon entering the repository, including sessions started without a skill. It is the only entry point devkit provides for such sessions.
- **Bundle Fragments**: A bundle adds lines with a `guidance` asset (Markdown list items, at most 300 bytes each). A fragment is reserved for a pointer every session needs at a moment no skill marks, stated with its read condition, for example the `git-commits` line "Before drafting or creating a commit message, read `<path>`". `{path:<asset-id>}` resolves to the file agents read (the override, else the managed copy). Fragments follow devkit's own lines, ordered by bundle and asset id, so the block changes only with the selection.
- **Token Budget**: devkit's own lines stay under 1 KB; each selected fragment adds at most 300 bytes. The block never contains project-specific policies or domain rules: fragments point to them, and bundle-level guidance stays in each bundle's constitution and instructions, reached through `get-context`. The opt-in `RULE-agent-guide-size` measures the whole root guide, block included.
- **Target Location**: Host project root `AGENTS.md`. Generated from the current selection and hash-guarded through the receipt; bytes outside the markers are project-owned. `guidance_block = false` in `.devkit/config.toml` turns it off. `CLAUDE.md` is never written; projects that need one point it at `AGENTS.md` themselves. See `CAP-DIST-workspace-ownership`.

#### 2. `package-constitution`
- **Role**: The foundational architecture guide of a bundle or domain (repository rules, backend conventions, testing architecture).
- **Consumption**: Before the first skill from the bundle is performed, run `uv run devkit get-context <bundle>`, whose response always includes the complete constitution. Load once per bundle per agent context, shared across all its skills; reload only when the guidance is no longer available (after compaction, in a new agent context).
- **Token Budget**: Strictly bounded (~50–100 lines): core contracts and pointers to granular `package-instruction` documents.
- **Target Location**: `.devkit/managed/<bundle>/AGENTS.md`.

#### 3. `package-instruction`
- **Role**: Natural-language coding standards, API design rules, domain constraints, and architectural guidelines that require developer judgment.
- **Consumption**: Progressive disclosure, like agent skills: `get-context` exposes the YAML headers and readable file paths of synchronized instructions, never their bodies. The agent selects relevant instructions by name and description and reads their files only when needed. No instruction body is eagerly included in the default context.
- **Token Budget**: Headers consume context when the bundle is first used; bodies only when selected.
- **Target Location**: `.devkit/managed/<bundle>/instructions/<name>.md`.
- **Format Requirements**: Single Markdown document with English YAML frontmatter specifying `name` and `description`.

#### Bundle context delivery contract

The **bundle context** is the whole `get-context <bundle>` response: the constitution (when present, read in full) plus the instruction header catalog (read selectively). The response, the skill body prerequisite that `devkit sync` injects and the once-per-bundle rule are specified in `CAP-DIST-context-and-playbooks` (section 2). In addition:

- Authoring ZIP exports, like source files, never receive the prerequisite.
- Other package entry points may request the same context with the same command and the same once-per-bundle rule.
- The command is stateless: context deduplication is the agent's responsibility; automatic injection and exactly-once runtime enforcement are not guaranteed.
- Installation, listing, and skill discovery do not load the context. Instruction bodies remain on demand after `get-context` runs.

#### 4. `package-playbook`
- **Role**: Procedures for occasional tasks, retrieved for reuse and extended through experience. Explicit, recurring execution flows belong to workflows; frequency alone does not turn a policy or judgment criterion into a playbook.
- **Consumption**: Only through two entry conditions, never through implicit scanning during ordinary tasks (which adds latency, prompt bloat and hallucinated runbooks):
  1. **Explicit user invocation** of the shared `devkit-playbook` skill (`"use devkit-playbook to recover the replica"`).
  2. **Rule-triggered remediation**: a `governance-rule`, evaluated out-of-band by `devkit.rules` (`just rules-check`, CI, the `rules-check` commit gate) at zero token cost, reports a violation whose `Violation.remediation` points to the playbook (a search query or path) instead of embedding the procedure in the rule.

  Individual playbooks are not exposed in the default context, `get-context` or the native skill catalog, and ordinary prompt instructions do not bypass these entry conditions.
- **Format Requirements**: English YAML frontmatter with required `name` and `description`, plus an optional `aliases` string array. The body contains explicit `Prerequisites`, numbered `Step N` actions, and unambiguous completion conditions.
- **Target Location**: `.devkit/managed/<bundle>/<source path>`: a single Markdown file (for example `playbooks/<slug>.md`) or a directory whose entry is `<dir>/SKILL.md`.

#### 5. `package-workflow`
- **Role**: A declarative multi-stage delivery procedure (`devkit.workflow` definition) that every agent host follows from the same computed stage. Explicit, recurring execution flows belong here rather than in playbooks.
- **Consumption**: The generated `devkit-workflow` entry skill (present only when a workflow asset is synchronized) runs `devkit workflow next`, and stage skills named by the definition perform the work. Definitions are discovered through the installation receipt; a project-local definition with the same id shadows the distributed one.
- **Target Location**: `.devkit/managed/<bundle>/<source path>` with the path recorded in the receipt's `entrypoints`.

#### 6. `package-document`
- **Role**: Plain files with no engine semantics. Unseeded, a document is reference material (a template, a glossary, a schema) that agents and tools read by path. With `seeded = true` and a workspace `target`, it is project scaffolding (a documentation tree, a policy file the project will edit): `devkit sync` writes it once, when the target is absent, and never touches it again. Scaffolding is not a resource kind of its own, and seeded files are the only bundle output the project owns from the first sync on; everything else stays devkit-owned and hash-guarded (see `CAP-DIST-workspace-ownership`).
- **Consumption**: Read by path when another asset or instruction points to it; never catalogued by `get-context`, playbook search or projections.
- **Target Location**: `.devkit/managed/<bundle>/<source path>` (unseeded) or the declared `target` (seeded).

#### Instruction and playbook consumption boundaries

| Concern | `package-instruction` | `package-playbook` |
| --- | --- | --- |
| Purpose | Rules, constraints, and judgment criteria for the current work | Procedures for occasional tasks |
| Default disclosure | Headers and paths in the bundle's `get-context` response | No individual headers or bodies |
| Entry condition | The agent determines relevance from the instruction catalog | Explicit user invocation of `devkit-playbook`, OR explicit remediation guidance from a failing `governance-rule` |
| Full text | Read when relevant, before the affected action | Read after selecting a search candidate, before executing its procedure |
| Example | Compatibility requirements for database changes | Recovery steps for a particular database failure |

An explicit invocation applies to the requested task, not to all future tasks in the conversation: "recover the database" alone does not initiate playbook search; "use devkit-playbook to recover the database" does. A selected playbook does not replace package guidance: load its bundle's context if it is not already available, then apply the constitution and any relevant instructions. The once-per-bundle rule concerns context loading, not the procedure's execution state.

**Example of the rule-triggered pattern.** The opt-in `authoring` bundle's `agent-guide-authoring` preset pairs the hygiene rule `RULE-agent-guide-size` (mechanical detection: an `AGENTS.md` or `CLAUDE.md` above 8 KB, with the devkit block's share) with the `agent-guide-authoring` playbook (procedural resolution: keep what nearly every task needs and move the rest to READMEs, instructions, playbooks, rules or nested guides); its remediation names `uv run devkit playbook search "curate agent guide"`. Root guides are injected on every turn, so the recommended budget is 4 KB to 8 KB. The `skill-authoring` preset applies the same pattern to skills and playbooks (`RULE-skill-document-size`). See [devkit.rules](../development/reference/rules.md#built-in-authoring-bundle).

#### `devkit-playbook` entry point and search contract

`devkit sync` generates one shared `devkit-playbook` skill when selected playbooks exist (Codex: `policy.allow_implicit_invocation: false`; Claude Code: `disable-model-invocation: true`; other hosts follow the skill body). After an explicit invocation the agent turns the task into an English query, runs `uv run devkit playbook search "<English query>"`, reads the selected candidate's full procedure and checks its prerequisites before executing it. A search match ranks relevance only; it grants no extra permission. When nothing fits, the agent completes the task and offers a playbook draft, persisted only with the user's approval and never into managed copies. The search contract (indexed fields, modes, `[playbooks]` defaults and bounds, the byte budget, frontmatter rules) is specified in `CAP-DIST-context-and-playbooks` (section 3); the rankings are `CAP-SRCH-document-search`'s.

**Open item: optional query for bundle context.** `devkit get-context <bundle>` takes no query. A future optional English query could narrow instruction header exposure as catalogs grow; it would have to keep the full constitution in every response, keep instruction bodies on demand, keep the no-query behavior, and must not enable playbook discovery during ordinary task handling. This is a review item, not a planned command signature.

### B. Mechanized Execution Layer (Code & Native Tooling)

#### 7. `governance-rule`
- **Role**: Invariants that can and must be 100% mechanically verified via parsing, regex, or static analysis.
- **Consumption**: Evaluated out-of-band by `devkit.rules` during `just rules-check`, `devkit rules check`, the `rules-check` commit gate, or CI (`check --ci`). `devkit sync` records every deployed rule file in the installation receipt and `devkit rules` loads each asset from there as one plugin package; a consumer tunes a rule's phase, severity and typed settings in `[rules]` of `.devkit/config.toml`, never by editing the managed files.
- **Format Requirements**: A plugin package directory: the rule module, optional `__init__.py`, helper modules imported relatively, the guide, resources and the rule's tests in `tests/` (`CAP-GOV-rule-authoring`; run with `devkit rules test`, `CAP-GOV-rule-authoring`).
- **Token Budget**: Zero LLM context unless violations are reported. A rule may ship a Markdown guide that `devkit rules explain` prints on demand.
- **Target Location**: `.devkit/managed/<bundle>/<source path>` (for example `rules/<rule>/`).

#### 8. `agent-skill`
- **Role**: Reusable capability packaged as a tool directory containing a `SKILL.md` manifest, executable scripts (`0755`), references, and templates.
- **Consumption**: Projected into vendor-neutral or agent-specific tool roots (`.agents/skills/<name>/`, `.claude/skills/<name>/`) and invoked as tools.
- **Target Location**: Native agent skill directories.

#### 9. `agent-subagent`
- **Role**: Standalone agent persona definition configuring system prompts, permissions, and tool access for delegated subagent tasks.
- **Consumption**: Read by agent runtimes when spawning child tasks.
- **Format Requirements**: Either vendor-native files per agent (`.toml` for Codex in `.codex/agents/<name>.toml`, `.md` for Claude Code in `.claude/agents/<name>.md`, `.md` for Antigravity in `.agents/agents/<name>.md`), or one host-neutral role contract (Markdown with a `hosts` table of allowlisted per-agent keys and a status) that `devkit sync` renders into those native files. A contract may carry `x-<name>` extension keys for other tools; devkit never renders them.
- **Target Location**: Native agent persona directories; a contract itself stays under `.devkit/managed/<bundle>/`.

#### 10. `git-commit-gate`
- **Role**: Policy enforced at Git's `pre-commit`, `commit-msg` or `post-commit` hook: what may be committed, how the message must look, and what happens after the commit exists.
- **Consumption**: Run by `devkit.gate` through static hook wrappers that discover deployed gates from the installation receipt on every commit. Configured in `[gates]` of `.devkit/config.toml`, overridden per clone by `.git/devkit.config`. See `CAP-GATE-commit-gates`.
- **Token Budget**: Zero LLM context; refusals are Agent Advisory Protocol errors.
- **Format Requirements**: A plugin package directory whose modules define `BaseGate` subclasses.
- **Target Location**: `.devkit/managed/<bundle>/<source path>` (for example `gates/<gate>/`); manifest `kind = "gate"`.

## 4. Placement Decision Matrix

When authoring new project guidance or developer tooling, select the resource kind with this decision tree:

```text
Q1: Can this invariant be 100% deterministically verified by machine code?
 ├─ YES, a repository invariant ──> [ governance-rule ] (Python rule for devkit.rules)
 ├─ YES, commit-time policy (message, post-commit action) ──> [ git-commit-gate ] (devkit.gate)
 ├─ YES, a workflow stage condition ──> [ package-workflow ] exit check (a devkit.workflow primitive)
 └─ NO  ──> Q2

Q2: Is it a reusable tool or executable script directory for the agent?
 ├─ YES ──> [ agent-skill ] (Projected into .agents/skills/ or .claude/skills/)
 └─ NO  ──> Q3

Q3: Is it an agent persona definition or subagent configuration file?
 ├─ YES ──> [ agent-subagent ] (Projected into .codex/agents/, .claude/agents/ or .agents/agents/)
 └─ NO  ──> Q4

Q4: Is it a task procedure rather than a rule or judgment criterion?
 ├─ YES, recurring explicit flow ──> [ package-workflow ] (devkit workflow definition; see docs/capabilities/delivery/CAP-DLV-workflow-orchestration.md)
 ├─ YES, occasional procedure ──> [ package-playbook ] (Explicit devkit-playbook entry)
 └─ NO  ──> Q5

Q5: Is it a global orientation pointer required in root bootstrap files?
 ├─ YES ──> [ host-guidance-block ] (Generated by devkit sync into root AGENTS.md; not authored)
 └─ NO  ──> Q6

Q6: Is it a file read by path (template, schema) or scaffolding the project will own?
 ├─ YES ──> [ package-document ] (Managed copy, or seeded = true for write-once project files)
 └─ NO  ──> Q7

Q7: Is it a high-level package constitution loaded before the first bundle skill?
 ├─ YES ──> [ package-constitution ] (Stored in package AGENTS.md)
 └─ NO  ──> [ package-instruction ] (Default for policies, coding standards, and judgment criteria)
```

## 5. Selection and Packaging Mechanics

Asset filtering is governed by bundle-level manifest presets (`[presets.<name>]`, the reserved `all`, and the author's `default_preset`; see the `CAP-DIST-manifest-spec`) and the Git-tracked `[presets]` table of `.devkit/config.toml`. A bundle that declares `auto_select` is deployed with its `default_preset` without an entry; `devkit add <bundle>` writes an entry (resolving `default_preset`) and synchronizes; afterwards a plain `devkit sync` converges the workspace to the declared configuration. The selection model, its precedence and the built-in defaults are normative in `CAP-DIST-sync-and-transactions`.

### Architecture Decision: No Python Package Extras

Package extras (`[project.optional-dependencies]`) were rejected for asset selection:

1. **Wheel immutability**: a wheel unpacks its entire contents; extras control dependency resolution and cannot omit resource files within a wheel.
2. **No runtime introspection**: `importlib.metadata` does not expose which extras the consumer requested, so resolving them would mean ad-hoc parsing of the consumer's `pyproject.toml` or `uv.lock`.
3. **Micro-package explosion**: selective installation through extras would split cohesive bundles into micro-wheels (`pkg-core`, `pkg-git-commits`, ...), multiplying authoring, CI and version-synchronization cost.

### Architecture Decision: Author-Declared Auto-Selection

Installing a content wheel makes its bundle available. Whether that alone deploys it is the bundle author's call: a
bundle that declares `auto_select` is deployed with its `default_preset` as soon as its package is installed, and a
project opts it out with `[presets] <bundle> = false`; any other bundle is deployed only once `.devkit/config.toml`
selects it (`devkit add`). The bundles built into the devkit wheels follow the same rule (`devkit` and `advisory` of
`devkit-dist` and `harness` of `devkit-agt` declare `auto_select`; `git-commits` and `authoring` do not).

A project that installs a package built on devkit installed it to use it, so its default content should arrive
without a second step. Dependency resolution already decides what reaches the environment:

1. **Dev dependencies do not travel**: `[dependency-groups]` are left out of the built wheel, so a content
   package's own tooling never reaches its consumers.
2. **Runtime dependencies are intended**: a package that lists another content package in
   `[project.dependencies]` layers on it (a `team-backend` bundle on top of `company-base`), so deploying that
   bundle's default preset too is the expected result, not a leak. Installing a package already trusts its code; an
   auto-selected bundle adds no new trust.
3. **The change stays reviewable**: a new or upgraded package shows in the `uv.lock` diff, what it deploys shows in
   the Git-tracked `.devkit/installation.json` and root `AGENTS.md` diffs, and `BUNDLE_AUTO_SELECTED` tells the agent
   once per clone so it can report it to the user.

What remains configuration-driven: an explicit selection records the resolved preset name, so upstream can change a
preset's assets but not which presets a project chose; selections passed on the CLI are saved to `config.toml`, never
kept only in the receipt.

Availability follows dependency resolution for **adding** a bundle, never for removing one. The receipt and the root
`AGENTS.md` block are Git-tracked and shared, while the environment a sync runs in is not: a monorepo member synced
with `uv sync --package`, a `--no-dev` or `--only-group` CI job, or a production environment that carries devkit as a
runtime dependency of a package built on it can each lack a content package the lock still provides. So a bundle the
receipt records as deployed stays selected while its package is missing or cannot be loaded, and the sync fails
(`SELECTION_INVALID`, `BUNDLE_PACKAGE_INVALID`) until the package is installed again or `devkit remove <bundle>`
drops it. The cost is accepted: a package upgrade that drops a transitive content package stops `devkit sync` until
someone runs `devkit remove` and commits the result.

Alternatives considered:

- **Explicit opt-in for every content bundle** (the previous model): made each installed package a no-op until a
  second `devkit add`, to guard against transitive installs that dependency resolution already makes intentional.
- **Deploy every asset of every installed bundle**: rejected; a bundle's full asset set (`all`) is rarely what a
  project wants, so auto-selection deploys only the preset the author names as the default.
- **Automatic for direct dependencies only**: rejected because `importlib.metadata` cannot tell which packages the
  consumer requested directly, and the CLI may run in a tool environment (`uvx --with ...`) with no consumer
  `pyproject.toml` at all.

## 6. Summary Comparison Table

| Resource Kind | Tier / Layer | Typical File Form | Consumption Timing | Token / Context Impact | Physical Destination |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **`host-guidance-block`** | Guidance | Marker block written by `devkit sync` | Session bootstrap | Minimal pointer index (<1 KB, plus ≤300 B per bundle fragment) | Root `AGENTS.md` |
| **`package-constitution`** | Guidance | Markdown (~50–100 lines) | Before first bundle skill | Bounded (~100 lines) | `.devkit/managed/<bundle>/AGENTS.md` |
| **`package-instruction`** | Guidance | Markdown (`instructions/*.md`) | Headers on first bundle use; bodies on demand | Header catalog plus selected bodies | `.devkit/managed/<bundle>/instructions/` |
| **`package-playbook`** | Guidance | Metadata and checklist (`playbooks/<slug>.md` or `playbooks/<slug>/SKILL.md`) | Explicit `devkit-playbook` invocation OR rule-triggered remediation, then search and selection | Bounded candidate headers; selected body only | `.devkit/managed/<bundle>/playbooks/` |
| **`package-workflow`** | Guidance | Markdown definition with `stages` frontmatter | `devkit workflow next` via the `devkit-workflow` entry skill | Tagged CLI output per stage | `.devkit/managed/<bundle>/` (receipt `entrypoints`) |
| **`package-document`** | Guidance | Any file or directory | Read by path; seeded once when `seeded = true` | Only when read | `.devkit/managed/<bundle>/`, or the seed `target` |
| **`governance-rule`** | Mechanized | Python package dir (`rules/<rule>/`) | Linters / `just rules-check` | **0 tokens** (pure code) | `.devkit/managed/<bundle>/rules/` |
| **`agent-skill`** | Mechanized | Directory (`skills/<slug>/`) | Tool/function invocation | Tool registry metadata | Projected (`.agents/skills/`, etc.) |
| **`agent-subagent`** | Mechanized | Native config (`agents/<slug>.{toml,md}`) or role contract (`subagents/<slug>.md`) | Subagent delegation | Persona config on load | Projected (`.codex/agents/`, `.claude/agents/`, `.agents/agents/`) |
| **`host-hook`** | Mechanized | Declarative TOML (`hooks/<slug>.toml`) | Native host lifecycle event through `devkit host hook` | Bounded native context response | Managed definition plus exact shared host registration |
| **`git-commit-gate`** | Mechanized | Python package dir (`gates/<gate>/`) | Git commit hooks | **0 tokens** (pure code) | `.devkit/managed/<bundle>/gates/` |
