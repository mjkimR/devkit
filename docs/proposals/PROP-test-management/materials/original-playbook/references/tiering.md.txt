# Test Tiering and Growth Separation

## 1. Boundary definitions

Classify tests by the exercised boundary, not by execution duration:

| Tier | Exercised boundary | Permitted resources | Prohibited resources |
| :--- | :--- | :--- | :--- |
| `unit` | Pure domain logic, state machines, value objects, AST rules | In-memory objects, test doubles, stubs | Disk I/O, Git repository operations, subprocesses, sockets, databases |
| `integration` | Use cases, repository adapters, component composition, in-process HTTP | Temporary directories, in-memory SQLite, embedded in-memory vector stores, ASGI clients | Standalone daemon processes, external cloud APIs, shared persistent databases |
| `e2e` | Installed package entry points, CLI workflows, MCP servers, browser flows | Subprocess execution, real server boot, loopback sockets, browser drivers | Unbounded external network endpoints, real cloud credentials |

## 2. Growth separation policies

Apply separation policies progressively as the suite expands:

1. **Recipe separation for fast iteration**:
   - If total suite duration exceeds fifteen seconds, introduce a fast recipe (`just test-fast`) that excludes `e2e` tests.
   - Keep everyday developer verification under ten seconds. Run full end-to-end suites on demand, at integration, or during nightly checks.

2. **Classification mechanics**:
   - In multi-package or monorepo layouts, place tests in strict directories (`tests/unit/`, `tests/integration/`, `tests/e2e/`). Fail collection if an unclassified directory appears.
   - In single-package feature layouts, assign markers automatically using `pytest_collection_modifyitems` in the root test configuration based on file path patterns:
     - Paths containing `/server/` or `/e2e/` receive the `e2e` marker.
     - Paths containing `/integrations/` or `/jobs/` receive the `integrate` marker.
     - Remaining test paths receive the `unit` marker.

3. **Affected test execution**:
   - If a static dependency runner is available (`just test-affected`), run only tests affected by changed files compared to the base branch.
   - Exclude end-to-end tests from partial affected runs unless an end-to-end test file itself changed or an explicit flag is passed.

4. **Benchmark and stress test isolation**:
   - If tests process large data scales (such as indexing thousands of records or stress-testing concurrency queues), exclude them from regular test discovery.
   - Place scale benchmarks in dedicated benchmark recipes (`just baseline`) to preserve fast CI feedback.

5. **Hardware and environment skipping**:
   - If tests require specific hardware, mounted volumes, or external local servers, inspect availability in a setup fixture.
   - If the required environment is absent, call `pytest.skip` with an informative reason instead of failing the run.
