# Retain initial documents and roadmap

1. Review the compared directions and evidence before drafting; retain user decisions separately from recommendations and assumptions.
2. Choose documents that help the next decision; reuse useful existing files and combine a small investigation into one note.
3. With no existing destination, place project-owned discovery/planning notes under `docs/materials/`; read the installed docs writing instructions and use indexed material conventions only when identity is needed.
4. Ask discovery-planner for drafts when separate synthesis is useful; validate its claims against the actual sources, role returns and user decisions before saving.
5. Cover the logical contents below proportionately; label proposed behavior and conditional work as planned, not current capability or an accepted delivery commitment.
6. Update current `.devkit/incubation.md` with exact retained links, source identities, useful surviving alternatives, actual decisions, uncertainties, reopening conditions and the next useful action.
7. Before returning, inspect the written files and report actual paths, evidence coverage and unverified decisions; verify that the next action grants no authority absent from the user's request. Retain selected supporting evidence and important rejected alternatives, and resolve required references without transient-only files.

## Logical contents

| Content | What makes it useful |
| --- | --- |
| Product brief | Intended users, problem, representative usage, value hypothesis, constraints and proposed scope |
| Research and alternatives | Supported claims and sources, what was inspected, contradictions, unknowns and materially different candidate directions |
| Direction and architecture | Provisional recommendation, actual user decisions, assumptions, consequences, checks to run or defer, and conditions to reopen an alternative |
| Initial roadmap | Outcomes/questions by horizon, ordering/dependencies, validation signals and conditional implementation slices |

Do not require a fixed file count. A roadmap distinguishes learning work from build work and omits unsupported
dates or ownership promises. Link each consequential choice to its evidence or the missing check. A vendor
feature claim is not observed usability; a working technical experiment is not proof of demand.

Use native capability, use-case, decision or milestone documents only when their semantic subject and installed
authoring rules apply. A discovery roadmap does not automatically create milestones, proposals, work units or
a spec-package dependency. Do not describe planned features as implemented or interpret a draft as user approval.

Keep current facts and useful alternatives, not an immutable transcript or hidden reasoning log. Retain brief
decision rationale and source references; remove superseded experiments only when they no longer inform work.
Report unavailable evidence as unknown, and budget exhaustion as a bounded partial result.

Example roadmap item: "Determine whether shared edits overlap; depends on observing the current workflow.
Choose conflict handling only after that evidence. Implementation remains conditional on the product decision."
