# Idea discovery

Run only when the user explicitly invokes this entry.
Turn the supplied idea into proposals the owner can judge, with research serving decisions that need evidence.

## Boundaries

- Keep results in conversation by default; only the coordinator writes an explicitly requested retained result.
- Explore within the supplied goal and constraints; implementation, project settings, delivery Units, approvals,
  envelopes, staging, commits and publication require separate authority and the project's existing workflow.
- Keep user decisions, recommendations, assumptions and inspected facts distinct; team agreement grants no user decision.
- Delegate only bounded questions; roles return evidence or drafts and leave product files, the index and HEAD unchanged.
- Use only a verified ignored transient run for scratch; report denied access or missing capabilities without bypass.
- Require no fixed team, option count, questionnaire length, score, consensus, external research or report file.
- Preserve the owner's choice to clarify, explore or reject the idea without pushing it toward implementation.

## Procedure

1. Read the supplied context and relevant project evidence before asking questions; recover the desired change,
   audience and concrete use scene, consequential constraints and requested session outcome.
2. Interview only for unanswered user-only decisions whose answers change the first proposals or avoid substantial
   wasted exploration. Explain what each answer changes; use one question for dependent choices and a small batch
   for independent choices. Find inspectable facts yourself instead of asking the owner to retrieve them.
3. Once useful exploration is possible, state the first wave's question, observable effort bound and stop condition;
   leave deferrable preferences as explicit assumptions or alternative premises. Do not resolve every design branch
   before showing a proposal, and do not invent an audience or goal as a confirmed user decision.
4. Develop materially different plausible premises while direction is open; keep a small inquiry inline. Before
   delegating or allocating scratch, read `references/orchestration.md` and select only the needed explorer,
   researcher or challenger role. Give independent explorers common facts and constraints without peer conclusions
   or a preferred winner. Research a factual gap only when its answer can change a consequential choice.
5. Make concrete first proposals before asking the owner to settle downstream details. For each surviving direction,
   show an actual use example, expected benefit, adoption/operating cost, inspected support, unresolved assumptions
   and the condition that would rule it out. Explain a single surviving direction instead of filling an option quota.
6. After developing candidates, pressure-test consequential premises, evidence and missing alternatives; use the
   challenger when independent context helps. Accept zero supported findings and refine supported gaps without
   forcing agreement or eliminating an undeveloped premise merely because it lacks research yet.
7. Recommend from actual findings and read the routing table below; ask the owner only where their decision changes
   the route. Before another autonomous round, name the unresolved question and what result changes the recommendation;
   stop at the agreed bound or when no remaining inquiry changes the next decision.
8. Return the discovery outcome and next decision in conversation. If retention is explicitly requested, read
   `references/retention.md` before writing; report the actual path and identity or the blocked write. Describe a
   delivery handoff only when direction is sufficiently clear; start it only under separate user authorization.

## Route the remaining uncertainty

| Uncertainty | Next action |
| --- | --- |
| Owner's goal, preference or tradeoff | Show the concrete consequence and ask the focused choice; do not let a role impersonate the owner. |
| Inspectable fact or external evidence | Investigate that question within the bound; do not start another explicitly invoked entry. |
| Experience or behavior cannot be judged from prose | Show an inline example or sketch; propose a bounded experiment and obtain write/execution authority before running it. |
| Central premise fails | Reframe within the agreed goal, or recommend holding or rejecting the idea with the failure evidence. |
| Direction is clear enough for the requested use | Return a concise brief with decisions, reasons, rejected alternatives and consequential open assumptions. |

## Completion

- Return one outcome: `clarified`, `validation-needed`, `held` or `rejected`, with its reason and missing coverage.
- Show concrete candidate proposals and a recommendation when supported; distinguish actual user decisions from
  assumptions and evidence limits, and identify the next decision or discriminating check.
- Count a clearer or rejected idea as a valid result; create no mandatory delivery document or implementation task.
- Report actual role execution, unavailable evidence and any remaining work without claiming an unexecuted investigation.
- For a retained result, report its path, material ID and complete/partial status; leave it uncommitted and require
  commitment through project Git policy before downstream documents cite it.

Example: `/discovery I keep losing useful technical reading; help me decide what would actually improve that.`
