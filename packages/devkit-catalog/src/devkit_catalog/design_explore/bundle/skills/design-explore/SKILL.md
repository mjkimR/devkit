# General solution exploration

Run only when the user explicitly invokes this entry.
Help choose a useful way to solve the supplied design problem while preserving its actual goal and hard constraints.

## Boundaries

- Explore solution directions; implementation starts only through a separate request and the existing project workflow.
- Return in conversation by default; only the coordinator writes an explicitly requested destination under project rules.
- Delegated roles inspect assigned sources and return proposals or evidence; they write no product source or retained artifacts.
- Keep current settings and authority; invocation grants no commit, delivery approval or publication permission.
- Follow tool and access restrictions; stop a denied operation without another route around the refusal.
- Keep roles optional and local; role instructions provide no native permission or filesystem isolation.
- Require no fixed cast, option count, numeric score, consensus, research report, prototype or comparative-effectiveness experiment.

## Procedure

1. Recover the problem, intended benefit, existing design, hard constraints and open preferences from context; ask
   only for missing facts that change useful directions. A proposed solution is a starting point unless the user
   fixes it as a hard constraint.
2. Choose useful premises; keep a small question inline. Read `references/exploration-methods.md` when choosing or
   developing alternative mechanisms for an architecture, model, module boundary or workflow.
3. Before delegating, read `references/orchestration.md`. Reuse solution-explorer with different premises; select researcher and critic work only
   for a concrete question. Preserve independent first passes where supported and disclose inline fallback.
4. Compare actual returned mechanisms on complexity removed or added, responsibility, coupling, failure behavior and
   adoption cost; distinguish inspected evidence from inference and unknowns. Product brands, renamed components or
   role labels are not materially different mechanisms.
5. Preserve an unconventional plausible mechanism and its benefit instead of averaging candidates into a generic
   feature list. Use bounded criticism when it can change a consequential choice; zero findings is valid. When a
   supported objection can change the choice, use the optional response exchange in `references/orchestration.md`
   within the normal one critique/refinement pass, with no consensus or score threshold.
6. Return useful directions with their distinguishing mechanism, benefit, main tradeoff and decision-changing
   assumption; add an illustrative sketch, data shape, sequence or example when it explains the mechanism.
   Recommend a direction when justified and name any unresolved choice. Suggest a next check only for a concrete
   unknown that changes that choice; never make proof of team benefit a prerequisite.
7. If a destination is requested, preserve its format and writing authority; if unavailable or refused, keep the
   conversation result and name the blocked write. Create no document or delivery unit by default.

## Completion

- The result helps choose a design direction and names its consequential uncertainty without filling an option quota.
- The report states missing returns, uninspected evidence and context limitations without claiming creative superiority.
- A requested destination contains only the authorized result, or the report names why that write remains blocked.
- No implementation, settings change, commit, approval or publication follows from exploration alone.
