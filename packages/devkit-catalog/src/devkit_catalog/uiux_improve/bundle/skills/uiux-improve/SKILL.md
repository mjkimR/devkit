# UI/UX improvement

Run only when the user explicitly invokes this entry.
Improve the interface and experience serving the supplied user goal; choose flow, interaction and visual work
according to the request. A review-only request ends with findings and no product edits.

## Boundaries

- Follow the consumer's existing development workflow for implementation, records, checks and approvals.
- Keep the current development approach and authority; this skill grants no commit, integration or publication permission.
- Preserve supplied product and design-system constraints unless the user authorizes changing them.
- Use available tools and follow their access restrictions; a denied operation stops without another access route.
- Keep roles optional and local; load only selected role bodies for concrete assignments.
- Treat role instructions as behavioral guidance, not native permission or filesystem isolation.
- Do not require a fixed cast, alternative count, numeric score, exhaustive audit or comparative-effectiveness experiment.

## Procedure

1. Recover the target, intended user outcome, relevant artifacts and hard constraints from available context.
   Ask only for missing information that changes the work. For a broad request, choose a bounded initial focus
   and explain how it serves the goal.
2. Inspect the current interface and representative task path. Use the running UI when available; identify
   screenshot-, code- or text-only coverage when actual interaction cannot be checked.
3. Select useful design lenses. Read `references/design-guidance.md` when choosing or developing the design
   direction. Keep a small concrete request inline.
4. If independent perspectives can change the result, read `references/orchestration.md` before delegation.
   Assign only useful designer, unconventional-designer, reference-researcher or critic work; preserve independent
   first passes until their returns arrive.
5. Synthesize a coherent direction from the inspected artifacts and actual role returns. Produce alternatives
   when the choice matters. Preserve a useful unusual mechanism and its tradeoff instead of averaging every
   suggestion into a feature list. Resolve routine design choices within scope; raise product or scope choices
   that require the user.
6. Apply requested changes through the existing project workflow once its requirements permit implementation.
   Continue that workflow through the implementation, required checks and delivery approvals. When an approval
   or tool is missing, preserve useful work and name that concrete blocker.
7. Inspect the changed interface and representative interactions with the available tools. Check relevant
   layout states, feedback and recovery, keyboard/focus behavior and responsive behavior according to the change.
   Run the project's applicable checks. Fix defects exposed by these checks and recheck the changed behavior.
   If critique can improve the result, use one bounded critique/refinement pass; stop without a score or consensus quota.
8. Report the applied improvement, why it serves the user goal, what was actually checked and material limits.
   Honor a requested output destination; otherwise report in conversation. Product artifacts follow project ownership.

## Completion

- A normal improvement request finishes with the changed interface or flow and its verification status.
- A narrower request finishes with its requested findings or design artifact.
- A blocked request names the unresolved choice, artifact, workflow requirement or tool and retains useful partial work.
- Separate observed behavior, design inference and unavailable coverage; do not claim measured UX quality or team superiority.
