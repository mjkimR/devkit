# activity-effort

How thoroughly one activity of a slug is done: `low`, `medium` (the default) or `high`, chosen when the activity starts and passed to its executor as run input, never stored as authoritative state in the Unit or the configuration. Backlog and inline Planning have no effort: Backlog's work is fixed and inline Planning is the intent agreement only.

**Always propose it.** When an activity starts, state the effort you propose and why, and let the user confirm or override it; never apply the default silently. On a proposal, `proposal.md` carries non-authoritative recommendation hints `planning_effort` and `dev_effort` (`low` | `medium` | `high`, scaffolded as `medium` with `--planning-effort` and `--dev-effort`): Backlog sets both and proposes `planning_effort` (and provisional `dev_effort`) in the `plan-intent` request ([classification](classification.md) §1), Planning reviews and updates `dev_effort` in `proposal.md` before `plan-accept`, and `devkit spec proposal handoff` returns `dev_effort` in its output (`[HANDOFF: ... dev_effort=...]` / JSON `dev_effort`) without copying either field to `spec.md`. When starting Planning or Development of a proposal, read `planning_effort` or `dev_effort` (or `HandoffResult.dev_effort` after handoff) as the initial recommendation to confirm with the user; if the user overrides it at start, run at the chosen effort without a retroactive commit to `proposal.md`. `medium` is the default proposal, also for work that changes an accepted decision or contract, creates a contract or a document kind, or spans several packages: its `challenger` pass and initial review cover those. Propose `high` only when (a) the work has an effect that cannot be undone locally (a publication or release, a migration of persisted data, deletion of user data, or a change to a contract with external consumers such as the `devkit-advisory` API), or (b) an earlier activity or review of the same work left P1 findings unresolved, or the work was returned or closed for a defect. Propose `low` only for work whose direction leaves nothing to criticize.

| Activity | `low` | `medium` | `high` |
| --- | --- | --- | --- |
| Planning (`proposal`) | questions only; no `scout` or `challenger` | one `challenger` pass always; `scout` when the direction needs evidence | two or more options compared, `scout` and `challenger` required, rounds in the [review loop](review-loop.md) |
| Development (`session`) | the author's self-review | one mandatory initial `code-reviewer` pass; the implementer verifies fixes and decides repeat calls | `code-reviewer` subagent review in the [review loop](review-loop.md) |
| Development (Unit path) | the author's self-review and self-checked reconcile | one mandatory initial `code-reviewer` pass; a separate `reconcile-reviewer` check unless eligible for self-check below; repeat calls at the implementer's judgment | `code-reviewer` and a separate `reconcile-reviewer`, each in the [review loop](review-loop.md); the first reconcile verification is always independent |

Rules:

- **The floor stays.** Gates, the workflow's exit checks and `required` policies hold at every effort; effort sets only the optional procedure above them. On the Unit path the review envelope is recorded before `dev-integration` even at `low`; a `session` task reviews at every effort but records no envelope.
- **Review and evidence are separate.** `medium` and `high` always run the initial code review in a subagent, regardless of change size, for neutrality: a context other than the author's. A worker runs it nested (Host → worker → code-reviewer); a `session` task's Host or Cloud Agent runs it directly. The reviewer returns its fields as a message: on the Unit path the caller records them as the envelope, and a `low` self-review says so in its envelope; a `session` task reports the review method and result in its final response or PR body.
- **Reconcile is Unit-path only.** At every effort the implementer writes, fixes and resolves the Living Spec reflection and `reconcile.md`. The separate read-only `reconcile-reviewer` verifies it at `medium` and `high`, subject only to the medium exception below; a `session` task never calls that role. The implementer records every verification as a `reconcile-check` envelope at `living-spec-draft`, which exits only on the latest check with no open findings. Findings are fixed in the reconcile and checked again, never by reopening the code review.
- **Medium initial reconcile exception.** The implementer MAY omit the first `reconcile-reviewer` call only when all affected contracts and documents can be identified, their agreement with the actual diff can be directly demonstrated, and there is no unresolved contract interpretation or cross-component impact. Cross-component impact means the diff changes behavior or agent-facing text in more than one package, in more than one capability area, or in a package and the repository tooling (`scripts/`, `justfile`): a repository script plus a sentence of a shipped devkit-spec skill counts. The Living Spec reflection of the change itself, and links or references updated elsewhere, do not count. A confirmed no-impact or a wording-only reflection preserving the contract can qualify; a small diff alone cannot. If any condition is uncertain, call the reviewer. When omitting the call, perform the self-check and record both the omission reason and the verification evidence in the existing `reconcile-check` envelope, explicitly identifying it as self-verification. This exception never skips the first medium code review, changes the effort, or bypasses a required policy; `high` always calls the reconcile reviewer for its first round.
- **Medium repeat calls are discretionary.** After the initial code or reconcile review, the implementer verifies fixes and subsequent changes against the findings, affected requirements, checks and docs impact. Further subagent calls are the implementer's decision, not automatic after each edit; expanded scope, uncertain correctness or contract interpretation are reasons to call again. Close findings with evidence in `reverify`, or write a new `reconcile-check` for reconciliation, identifying who verified the changed scope; do not imply the prior reviewer checked later changes. An initial failed or stale call never satisfies a required first review. At `high` the review loop applies instead.
- **High runs a bounded loop.** Code review, reconcile verification and Planning criticism at `high` run in rounds of fresh reviewers until a round finds nothing or every fix of its batch is minor and self-verified; a batch still not minor at the cap (3 rounds after the initial one), a recurring P1 or a contested P1 goes to the user. Findings carry `P1`, `P2` or `P3`. Rounds, the minor-fix conditions, severity and the hand-over are in [review loop](review-loop.md).
- **High session work.** When `high` is proposed for a `session` task, the proposal SHOULD also advise on depth by what the work does: creating or changing a contract or a document kind proposes `spec` depth, reversing an accepted decision proposes `proposal` depth, and other work (a release or migration with no contract change, earlier unresolved findings, several packages alone) gets no depth advice. If the user keeps `session`, the work runs at `high` as defined: its review loop reports a hand-over in the conversation.
- **Effort and integration policy are independent.** `dev-integration = auto` applies at `low` too, once the path's self-review, required checks and completion conditions hold; `low` adds no human approval.
- **Where it is recorded.** A worker writes the effort it applied in its `worker` envelope (`--effort`, the sole authoritative record of applied effort; `proposal.md`'s `planning_effort` and `dev_effort` are non-authoritative hints only); a `session` task reports it in its final response or PR body. Model and reasoning settings are outside this axis.
