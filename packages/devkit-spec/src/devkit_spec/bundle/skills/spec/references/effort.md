# activity-effort

How thoroughly one activity of a slug is done: `low`, `medium` (the default) or `high`, chosen when the activity starts and passed to its executor as run input, never stored as authoritative state in the Unit or the configuration. Backlog and inline Planning have no effort.

**Always propose it.** When an activity starts, state the effort you propose and why, and let the user confirm or override it; never apply the default silently. For a proposal, the `planning_effort` and `dev_effort` hints in `proposal.md` (set in Backlog, `dev_effort` updated by Planning before `plan-accept` and returned by the handoff as `dev_effort`) are the initial recommendation; an override at start needs no commit to `proposal.md`. `medium` is the default proposal, also for work that changes an accepted decision or contract, creates a contract or a document kind, or spans several packages: its `challenger` pass and initial review cover those. Propose `high` only when (a) the work has an effect that cannot be undone locally (a publication or release, a migration of persisted data, deletion of user data, or a change to a contract with external consumers such as the `devkit-advisory` API), or (b) an earlier activity or review of the same work left P1 findings unresolved, or the work was returned or closed for a defect. Propose `low` only for work whose direction leaves nothing to criticize.

| Activity | `low` | `medium` | `high` |
| --- | --- | --- | --- |
| Planning (`proposal`) | questions only; no `scout` or `challenger` | one `challenger` pass always; `scout` when the direction needs evidence | two or more options compared, `scout` and `challenger` required, rounds in the [review loop](review-loop.md) |
| Development (`session`) | the author's self-review | one mandatory initial `code-reviewer` pass; the implementer verifies fixes and decides repeat calls | `code-reviewer` subagent review in the [review loop](review-loop.md) |
| Development (Unit path) | the author's self-review and self-checked reconcile | one mandatory initial `code-reviewer` pass; a separate `reconcile-reviewer` check unless eligible for self-check below; repeat calls at the implementer's judgment | `code-reviewer` and a separate `reconcile-reviewer`, each in the [review loop](review-loop.md); the first reconcile verification is always independent |

Rules:

- **The floor stays.** Gates, the workflow's exit checks and `required` policies hold at every effort; effort sets only the optional procedure above them. On the Unit path the review envelope is recorded before `dev-integration` even at `low` (a `low` self-review says so in it); a `session` task reviews at every effort (session: no records).
- **The initial review runs in a subagent** at `medium` and `high`, regardless of change size: a worker nests it (Host → worker → code-reviewer), a `session` task's Host or Cloud Agent runs it directly. The reviewer returns its fields as a message; on the Unit path the caller records them as the envelope.
- **Reconcile is Unit-path only.** The implementer writes and resolves the Living Spec reflection and `reconcile.md` at every effort; the read-only `reconcile-reviewer` verifies it at `medium` (except below) and `high`. Every verification is a `reconcile-check` envelope; `living-spec-draft` exits only on the latest with no open findings. Fix findings in the reconcile and check again, never by reopening the code review.
- **Medium initial reconcile exception.** The implementer MAY omit the first `reconcile-reviewer` call only when all affected contracts and documents can be identified, their agreement with the actual diff can be directly demonstrated, and there is no unresolved contract interpretation or cross-component impact. Cross-component impact means the diff changes behavior or agent-facing text in more than one package, in more than one capability area, or in a package and the repository tooling (`scripts/`, `justfile`): a repository script plus a sentence of a shipped devkit-spec skill counts. The Living Spec reflection of the change itself, and links or references updated elsewhere, do not count. A confirmed no-impact or a wording-only reflection preserving the contract can qualify; a small diff alone cannot. If any condition is uncertain, call the reviewer. When omitting the call, perform the self-check and record both the omission reason and the verification evidence in the existing `reconcile-check` envelope, explicitly identifying it as self-verification. This exception never skips the first medium code review, changes the effort, or bypasses a required policy; `high` always calls the reconcile reviewer for its first round.
- **Medium repeat calls are discretionary.** After the initial review the implementer verifies fixes and later changes itself and calls again only at its judgment (expanded scope, uncertain correctness or contract interpretation). Close findings with evidence in `reverify` or a new `reconcile-check`, naming who verified the changed scope; never imply the prior reviewer checked later changes. A failed or stale initial call never satisfies a required first review.
- **High runs the bounded [review loop](review-loop.md)** for code review, reconcile verification and Planning criticism; findings carry `P1`, `P2` or `P3`.
- **High session work.** When `high` is proposed for a `session` task, the proposal SHOULD also advise on depth by what the work does: creating or changing a contract or a document kind proposes `spec` depth, reversing an accepted decision proposes `proposal` depth, and other work (a release or migration with no contract change, earlier unresolved findings, several packages alone) gets no depth advice. If the user keeps `session`, the work runs at `high` as defined: its review loop reports a hand-over in the conversation.
- **Effort never changes integration policy** ([completion](completion.md#policy)).
- **Where it is recorded.** A worker writes the applied effort in its `worker` envelope (`--effort`, the sole authoritative record; the `proposal.md` hints are not); a `session` task reports it in its final response or PR body. Model and reasoning settings are outside this axis.
