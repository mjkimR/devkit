# Consuming devkit-managed assets

## What devkit owns

| Path | In Git | Role |
| --- | --- | --- |
| `.devkit/config.toml` | yes | Selection, presets, target agents and settings |
| `.devkit/config.local.toml` | no | Checkout-local preferences |
| `.devkit/installation.json` | yes | The receipt: every deployed file with its hash |
| `.devkit/overrides/<bundle>/` | yes | Project-owned replacements for upstream asset files |
| `.devkit/managed/`, `.devkit/transient/`, agent projections | no | Generated by sync |
| Root `AGENTS.md` | yes | Project-owned outside the `DEVKIT:START`/`DEVKIT:END` block |
| Seeded files | yes | Project-owned after the first sync; edit them freely |

Commit the tracked paths with the change that required them.

## Changing what is deployed

```bash
uv run devkit list                    # bundles, presets, selection, deployed paths
uv run devkit add <bundle>[:<preset>] # select, then sync
uv run devkit remove <bundle>         # deselect, then sync
uv run devkit sync                    # converge to .devkit/config.toml
uv run devkit sync --locked           # fresh clone, CI: restore ignored copies only
```

- Install a bundle's package (`uv add --dev <package>`) before selecting it.
- To learn what a setting does, run `uv run devkit config template --print`.
- For a `hook` asset, inspect registration with `uv run devkit host status --format json`;
  installation grants no host trust or execution permission.

## Checkout-local preferences

Put execution environment, tool registration, playbook search preferences and
scalar bundle variables in the ignored `.devkit/config.local.toml`; it is not a
secret store. `uv run devkit config show --effective --format json` shows the
values and their sources. Cloud execution means interactive approval is
unavailable, never approval to act.

## Customizing an upstream asset

```bash
uv run devkit override create <bundle>:<asset>   # copy the asset's files into .devkit/overrides/, then sync
uv run devkit override diff <bundle>:<asset>     # what upstream and the override changed
uv run devkit override accept <bundle>:<asset>   # record the current upstream as the baseline after merging
uv run devkit override remove <bundle>:<asset>   # use upstream again
```

- An override file replaces its upstream file everywhere agents read it; it
  follows upstream changes only through `accept`.
- For a `.md.jinja` asset, edit the template override and sync; agents read the
  rendered managed `.md`.
- Override only assets of selected bundles. Edit seeded files in place, and the
  repository's own assets in their source bundle (`in-repo-bundle`).

## Playbooks

If a failing rule's remediation names a playbook, run the `uv run devkit playbook search`
it names, load the playbook's bundle context if needed, then read and apply the
procedure at the returned path.

If the user names an exact playbook for this task, or configures an external
schedule with its ID:

1. Run `uv run devkit playbook get <bundle>/<playbook>`.
2. Unless already loaded in this agent context, run the context argv it returns.
3. Apply the constitution, then the body; read relative resources from the
   parent of `source.path`.

Check prerequisites, workflow gates, permissions and user constraints on every
execution. A schedule grants no future gated approval, and unavailable approval
UI is not approval.

## Completion

`uv run devkit status` and `uv run devkit sync --check` both exit `0`.
