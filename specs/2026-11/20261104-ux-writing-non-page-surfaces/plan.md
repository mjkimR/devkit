# Technical Plan: `SPEC-ux-writing-non-page-surfaces` UX writing guidance for surfaces beyond pages and forms

## 1. Constitution & Invariant Review

- `ADR-ux-screens` fixes one `ux` kind with `element` in `screen`, `modal`, `panel`, the five sections and the
  seven-column Interactions table. The guidance maps surfaces onto that vocabulary and changes none of it, so no ADR
  is needed.
- `ADR-explicit-ux-coverage-exception-notation` gives `global: <reason>` and `off screen: <reason>`; the guidance
  tells the agent when to use them for continuous input and system judgements, within their recorded meaning.
- `CAP-HARN-agent-guidance` 4.3: one owner per writing rule. The step citation criterion goes into
  `usecase-writing` (the owner of step citations); `ux-writing` refers to it. Every instruction `description` starts
  with `Read before` and stays within 300 characters (`test_writing_guidance.py`).
- The `authoring` bundle's `agent-asset-writing`: the instruction cites no repository document ID, writes one
  directive per line, one example per pattern and no hedges or emphasis (`RULE-agent-asset-wording`).
- No code, rule or engine change: `CAP-GOV-spec-rules` 3.15 and 3.16 are unchanged, and the rule tests added only pin
  behavior the rules already have.

## 2. Architecture Overview & Impact

- Target Area: the docs bundle of `devkit-docs` (`packages/devkit-docs/src/devkit_docs/bundles/docs/bundle/`) and the
  harness capability that catalogs its instructions.
- `instructions/ux-writing.md`: a new H2 `Surfaces beyond pages and forms` between `One element, linked both ways`
  and `Purpose and content`, holding six criteria (AC-01 to AC-04, AC-06, AC-07) as one directive per list item with
  one example each, and a pointer to `usecase-writing` for step citations. The `description` gains "surfaces beyond
  pages and forms" within 300 characters.
- `instructions/usecase-writing.md`: one list item under `Main Success Scenario` for long-running activities and
  system judgements (AC-05).
- `templates/ux.md`: the Interactions comment reads "One row per trigger that serves a step or is a global control;
  continuous input is described in Content and States" (AC-02); sections, frontmatter lines and the header row the
  guidance tests pin stay as they are.
- `docs/capabilities/harness/CAP-HARN-agent-guidance.md` 4.3: the `ux-writing` row names the surface criteria
  (AC-08). Written at `living-spec-draft` by `spec-sync` and listed in `reconcile.md`.
- Tests: `packages/devkit-spec/tests/integration/bundles/spec/test_ux_guidance.py` gains one test asserting each
  criterion block with `assert_rule` (AC-01 to AC-05, AC-07) and the template comment (AC-02);
  `rules/ux_links/tests/test_rule.py` and `rules/ux_coverage/tests/test_rule.py` each gain one test for a `screen`
  and a `panel` with `usecases: []` and a header-only table (AC-06).
- Deployed copies: `devkit sync` projects the instructions into consuming repositories; this repository's
  `.devkit/managed/docs/` copy is regenerated by the sync the change implies and never edited.

## 3. Component & Interface Design

The new section, as the agent reads it (normative wording lives in the instruction itself):

```markdown
## Surfaces beyond pages and forms

- Element: the surface a person perceives as one place while it is shown (a game viewport, a kiosk's attract
  loop, a terminal pane, a map) is a `screen`; an overlay shown beside or over it throughout (a HUD, a status bar, a
  toolbar, a transcript) is a `panel` the screen's Content names; an overlay that interrupts it until dismissed (a
  pause menu, a confirmation, a command palette) is a `modal`.
- Continuous input: write the control scheme (movement, aim, scrubbing, pan and zoom, speech, gestures) in Content
  and States; write a row only for a trigger that advances a use case step or is a global control
  (`global: <reason>`). The table does not list every input.
- Modes: when the surface has modes rather than data states, the modes are the state names and the From and To
  cells; write `populated`, `empty`, `loading` and `error` only where they apply.
- Transitions: a change that replaces what the person sees is a row whose Target is another UX document; a change
  of mode on the same surface is a row whose From and To differ with an empty Target.
- Steps: cite the element where a step's outcome is perceived, per `usecase-writing`.
- No task flow: leave `usecases` empty, keep Purpose, Content and States and the Interactions header; neither UX
  rule reports the document.
- Mismatch: if the surface still cannot be written under these criteria, record the document and the mismatch as
  feedback; that record is the evidence a rule change needs.
```

## 4. Error Handling & Edge Cases

- A `modal` without a task flow still needs a `close` or `back` row (`RULE-ux-links`); the section's task-less
  criterion names `screen` and `panel` and keeps the modal rule from `One element, linked both ways`.
- A use case step that cites a task-less screen while the screen's `usecases` stays empty is a `RULE-ux-links`
  finding; the section says that a step citation makes the surface a listed one.
- The `ux` template comment change must keep `COLUMNS` and the five headings intact: `test_ux_guidance.py` pins them.
